### Shared Responsibilities

All members agree to:

-   Contribute to both frontend and backend development when required.
-   Create and update Jira tasks for their work.
-   Use Git for version control and follow the team's branching and

-   Review teammates' code when requested.
-   Test their own work before considering a task complete.

### Communication Rules

1.  Team members should respond to important team messages within **24
    hours** on normal working days.
2.  Urgent issues that block another member's work should be
    communicated as soon as possible.
3.  Important decisions should not remain only in private conversations;
    they should be recorded in the appropriate team channel or project
    documentation.
4.  Team members should inform the group in advance if they are
    unavailable or cannot meet an agreed deadline.
5.  Technical questions should be discussed openly so that other members
    can learn from the discussion and the final decision can be
    documented.
6.  Communication should remain respectful, constructive, and focused on
    solving problems.

### Meetings

The team will follow the Scrum process required by the assignment:

-   **Sprint Planning:** Once at the beginning of each Sprint.
-   **Scrum Meetings:** Two meetings during each Sprint.
-   **Sprint Review:** Once at the end of each Sprint.
-   Additional meetings may be arranged when necessary.

Meeting notes and important decisions should be recorded when
appropriate.

## 3. Work Schedule and Deadlines

The team will organize work according to the Scrum Sprint structure
specified for the project. Each PA Sprint is approximately **2--3
weeks**.

### General Workflow

1.  Break project requirements into manageable tasks.
2.  Create all tasks in Jira before starting the corresponding work.
3.  Assign each task to exactly one responsible member.
4.  Define an expected completion date.
5.  Work on the task using Git and the agreed development process.
6.  Test and review the implementation.
7.  Update the Jira task status and completion information.
8.  Merge completed work into the appropriate branch after review.
9.  Update relevant documentation.

### Milestones

  Milestone                            Target     Responsible
  ------------------------------------ ---------- ----------------------------------
  Project setup and repository setup   \[Date\]   All members
  Requirements / initial analysis      \[Date\]   All members
  UI/UX preparation                    \[Date\]   UI/UX Lead + team
  Backend / database preparation       \[Date\]   Backend Lead + team
  Core feature implementation          \[Date\]   Assigned members
  Integration and testing              \[Date\]   Testing Lead + all members
  Documentation completion             \[Date\]   Documentation Lead + all members
  Final review and submission          \[Date\]   Project Manager + all members

### Availability and Contingency

-   Members should communicate known periods of unavailability before
    task assignment.
-   If a member cannot complete a task on time, they must notify the
    team as early as possible.
-   If a task becomes blocked, the team will redistribute or split the
    work when necessary.
-   High-priority tasks should have enough buffer before the final
    deadline to allow testing and fixing.
-   The team will prioritize completing critical functionality before
    optional improvements.

## 4. Code and Documentation Standards

### Coding Standards

The team agrees to:

-   Follow consistent naming conventions for variables, functions,
    classes, files, and components.
-   Keep functions and components reasonably small and focused.
-   Avoid unnecessary duplication of code.
-   Write clear and maintainable code.
-   Use meaningful commit messages.
-   Remove debugging code and unnecessary comments before merging.
-   Keep configuration and secrets out of the Git repository.
-   Never commit passwords, API keys, access tokens, or other sensitive
    credentials.

### Git Workflow

The team will use GitHub as the main repository.

General workflow:

1.  Pull the latest changes before starting new work.
2.  Create a branch for a feature, fix, or task when appropriate.
3.  Implement and test the changes locally.
4.  Commit changes with clear messages.
5.  Push the branch to GitHub.
6.  Create a Pull Request when code review is required.
7.  Review the changes before merging.
8.  Resolve conflicts carefully and verify the application after
    merging.

### Code Review

Code reviews should check:

-   Correctness and functionality.
-   Readability and maintainability.
-   Consistency with project conventions.
-   Potential bugs or edge cases.
-   Security issues such as exposed credentials.
-   Test coverage where appropriate.

The author of the code remains responsible for understanding and
validating the final implementation, including code generated or
assisted by AI tools.

### Documentation Standards

Project documentation should:

-   Be written in **English**.
-   Use **Markdown** where required.
-   Use Mermaid diagrams whenever appropriate.
-   Keep instructions and technical information synchronized with the
    actual implementation.
-   Clearly document important architecture and design decisions.
-   Include setup instructions when needed.
-   Identify the person who performed, reviewed, or edited each
    report/document section as required by the assignment.

## 5. Accountability and Performance

### Contribution Criteria

Each member's contribution will be evaluated based on:

-   Completion of assigned Jira tasks.
-   Quality and correctness of implementation.
-   Participation in team meetings and discussions.
-   Timely communication.
-   Code review and testing contributions.
-   Documentation contributions.
-   Ability to support teammates.
-   Compliance with Git, Jira, and project standards.

### Jira Accountability

For every task:

-   The task must be created before work begins.
-   Each task must have exactly one assignee.
-   The task should include an appropriate creation/assignment date and
    completion date.
-   The task status must reflect its actual progress.
-   Completed work should be supported by relevant evidence when
    appropriate.

### Handling Underperformance

If a member is unable to complete assigned work:

1.  The member should inform the team as soon as possible.
2.  The team will identify the reason for the delay or issue.
3.  The team will provide reasonable support or clarification.
4.  The task may be divided or reassigned if necessary to protect the
    Sprint goal.
5.  Repeated lack of participation or failure to communicate will be
    discussed by the team.
6.  If the problem cannot be resolved internally, the team may escalate
    the issue to the TA or instructor.

The goal of accountability is to maintain a fair workload and ensure
that every member contributes meaningfully.

## 6. Decision-Making Process

The team will use the following decision-making process:

### Normal Decisions

1.  The relevant members present the problem and possible solutions.
2.  The team discusses the advantages, disadvantages, and impact of each
    option.
3.  The team attempts to reach a consensus.
4.  If consensus cannot be reached within a reasonable time, the team
    will use a **majority vote**.
5.  The final decision should be recorded when it affects project
    architecture, requirements, workflow, or other important project
    matters.

### Role of the Project Manager

The Project Manager / Scrum Coordinator facilitates discussions and
helps keep decisions aligned with the Sprint goal and project deadlines.

The Project Manager does **not** have unlimited authority over technical
decisions. Technical decisions should be discussed with the relevant
members, and important disagreements should follow the
conflict-resolution process below.

### Urgent Decisions

When an urgent decision is required to prevent a major blocker:

-   The available members may make a temporary decision.
-   The decision should be communicated to the full team afterward.
-   The team may review and revise the decision if necessary.

## 7. Conflict Resolution

The team will handle conflicts using the following escalation process:

### Step 1 -- Direct Discussion

The members involved should discuss the issue directly and respectfully.
The discussion should focus on facts, project requirements, and possible
solutions rather than personal criticism.

### Step 2 -- Team Discussion

If the conflict cannot be resolved directly, the issue will be discussed
with the whole team. Each side should have an opportunity to explain its
position.

### Step 3 -- Evidence-Based Decision

The team will compare the alternatives based on:

-   Project requirements.
-   Technical correctness.
-   Maintainability.
-   Development effort.
-   Project deadlines.
-   User needs.
-   Impact on other features.

The team will attempt to reach consensus. If consensus is not possible,
a majority vote may be used.

### Step 4 -- Escalation

If the team cannot resolve a significant conflict internally, the issue
may be escalated to the **TA or instructor** for guidance.

### General Principles

-   Personal attacks and disrespectful communication are not acceptable.
-   Members should raise problems early rather than allowing them to
    become larger issues.
-   Decisions should prioritize the success and quality of the project.
-   Resolved conflicts and important decisions should be documented when
    they affect the project.

## 8. Review and Update Process

This Team Contract is a living document and may be updated when the
team's working conditions change.

### Review Schedule

The team will review the contract:

-   At the beginning of the project.
-   At the end of each Sprint.
-   Whenever there is a significant change in team responsibilities,
    workflow, or project requirements.
-   Whenever recurring communication or collaboration problems are
    identified.

### Update Procedure

1.  A member proposes a change and explains the reason.
2.  The team discusses the proposed change.
3.  The team reaches consensus or uses a majority vote if necessary.
4.  The Documentation Lead updates the Team Contract.
5.  The updated document is committed to the Git repository.
6.  The team members are informed of the change.
